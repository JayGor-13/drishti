# Code changes made on 2026-09-28 (review of results_training_2 and the draft paper)

Written in plain words. Every change below says **what was wrong**, **what changed**, and **why**.
Nothing here changes the model architecture; the trained checkpoints still load.

## 1. Heatmap training target: peak is now exactly 1.0 (the big one)

**Files:** `drishti_v2/training/stage_losses.py` (`make_gt_heatmaps`), `drishti_v2/models/motion_cnn.py`
(`MotionCNN.make_gt_heatmap`), `drishti_v2/training/focal_loss.py` (`heatmap_focal_loss`).

**What was wrong.** The CenterNet-style focal loss counts a heatmap pixel as a "positive" only when the
target map is exactly 1.0 there. The Gaussian target was drawn around the *fractional* drone centre
(for example pixel 35.2, 68.7), so no integer pixel ever reached 1.0. Result: the loss had zero positives
every step, only the "push everything to zero" term was active, and the MotionCNN learned an all-zero
heatmap. You can see this in the logs: `train_heatmap` drops from 206 to 0.00001 within three epochs of
stage 1, and on validation the heatmap peak is within 5 px of the drone in only 0.2% of frames.

**What changed.** The Gaussian is now centred on the *rounded* integer pixel, so its peak is exactly 1.0
(this is what the original CenterNet code does). The sub-pixel remainder is left to the existing offset
head, which is exactly what that head was designed for. The focal loss also accepts `target >= 0.9999`
as positive so half-precision targets cannot miss the peak.

**What to expect.** Stage 1 must be retrained. The heatmap loss will now stay in the 1 to 10 range instead
of collapsing, and `heatmap_peak_within_5px` should climb well above 50%. Two new tests in
`tests/test_heatmap_targets.py` lock this in.

## 2. Evaluator now reports where detections come from

**File:** `drishti_v2/evaluation/evaluator.py`.

**Why.** The paper claims detections are motion-guided, but nothing measured it. The evaluator now writes,
for every evaluation:

- `top_box_source_{motion,edge,grid,guided,pad}`: the share of frames whose top-scoring box came from each
  crop source.
- `true_positive_source_{...}`: the same, but only for top boxes that are correct (IoU >= 0.5).
- `gt_inside_some_crop`: how often the drone actually lay inside any 64 px crop window. If this is low,
  the crops are not covering the target and the box head cannot localise it (its centre output is
  bounded to the crop window).

These appear in `*_eval_metrics.json` and `history.csv` automatically.

## 3. New: sequence-level streaming evaluation (`drishti_v2/experiments/run_sequence_eval.py`)

**What was wrong.** The existing evaluator scores only the last frame of each 5-frame clip, samples one
clip every 24 frames, and never uses the tracker. The "Anti-UAV tracking accuracy" it prints is
therefore over a subsample, without tracking. That is not the benchmark protocol.

**What the script does.** Walks every frame of every sequence in order through `forward_stream`
(strictly causal), feeds the tracker's predicted centres back as guided crops (switch off with
`--no-tracker` for the ablation row), computes all metrics per sequence and averages over sequences.
Writes `per_sequence_<split>_<tag>.csv` and `summary_<split>_<tag>.json`, and prints FPS.

```
python -m drishti_v2.experiments.run_sequence_eval --config configs/default.yaml \
    --frames-root /home/newuser1/dataset_frames --split val \
    --checkpoint results/.../finetune_best.pt --device cuda
```

Use `--max-sequences 2 --max-frames 200` for a quick smoke run. Test: `tests/test_sequence_eval.py`.

## 4. New: parameter and FLOP accounting (`scripts/count_flops.py`)

**Why.** The draft quotes 44.8 M parameters and 11.4 GFLOPs versus 28.5 dense; none of that came from a
script. Measured with this script on `configs/default.yaml`:

| Quantity | Measured |
| --- | --- |
| Parameters, total | 6.97 M |
| of which crop encoder / MoE experts / temporal / MotionCNN | 3.61 M / 2.10 M / 1.12 M / 0.06 M |
| GFLOPs per streaming frame (sparse top-2) | 4.28 |
| GFLOPs per streaming frame (dense MoE) | 4.31 |
| Compute saved by sparse routing | 0.6% of the total |
| GFLOPs without LDMI | 4.07 |
| GFLOPs in the 16-crop dense fallback mode | 6.88 |

The script pins the motion gate (never dense for the main count, always dense for the fallback row) so the
numbers are deterministic; with untrained gate weights the mode would otherwise flip between runs.

The MoE is a tiny part of the compute (0.008 GFLOPs). The paper's compute-saving claim must be rewritten.

## 5. Ablation script loads a trained checkpoint (`drishti_v2/experiments/run_ablation.py`)

**What was wrong.** It built a fresh random model per variant and evaluated it, so its numbers were noise.

**What changed.** `--checkpoint` loads every tensor whose name and shape match. Variants where some
tensors could not be loaded (for example `no_ldmi`, which changes the MotionCNN input channels) are
flagged `retrain_required` in the CSV and must not be reported; they need their own training run.
Inference-time variants (edge crops off, scan period, number of crops) are valid as-is.

## 6. `train_full.py` uses the right learning rates

**What was wrong.** Every stage used `config.smoke_lr` (1e-4). The logged run used 1e-4, 5e-5, 1e-5, 2e-6
for stages 1 to 4, and stage 3 and 4 at 1e-4 would wreck the MoE and the fine-tune.

**What changed.** A per-stage learning-rate table matching `run_training.STAGE_DEFAULTS`; epoch counts
now also match the logged run (80 / 30 / 20 / 10).

## 7. Faster crop matching (29 Sep, `drishti_v2/assignment.py`)

**What was wrong.** The Hungarian matching read its cost matrix one tensor element at a time inside
Python loops (about 160,000 tiny tensor reads per forward pass), which is very slow on Windows.
**What changed.** The matrix is converted to a plain Python list once. Same algorithm, identical
results (checked against brute force on 300 random matrices).

## 8. The crop encoder now actually learns (5 Oct; THE second big one)

**What was wrong.** The crop encoder (the CNN that looks at each 64 px crop; 3.6 M of the model's
7 M parameters) was created with random weights and frozen. Nothing ever loaded pretrained weights,
and stages 1 to 3 never train it. Checked on our checkpoints: its weights changed by exactly 0 from
epoch 1 to epoch 20 on Anti-UAV300 and again on Anti-UAV410. In your original run it was only
unfrozen in the last stage at learning rate 2e-6, which moved it by at most 0.001. So every result so
far (your 67% and our 75.8% mAP@50) came from a detection head reading random features. Symptom on
Anti-UAV410: the drone was inside a crop in 88% of frames but found in only 62%, precision stuck near
43%, and stage 1 plateaued after a few epochs.

**What changed** (all behind config keys; defaults reproduce the old behaviour for ablations):
- `train_encoder_in_stage1: true` trains the encoder together with the MotionCNN and head in stage 1.
  It is frozen again in stages 2 and 3 (stability) and fine-tuned in stage 4 as before.
- `encoder_backbone: resnet18` swaps the small CNN for the first part of an ImageNet ResNet-18
  (stem, layer1, layer2), loaded from the official weights file
  (`resnet18-f37072fd.pth`, from https://download.pytorch.org/models/resnet18-f37072fd.pth) given in
  `encoder_pretrained_path`. For infrared with three crop scales, the three scales fill the three
  RGB input channels, so the pretrained first layer is used unchanged.
  It is also cheaper: whole model 4.57 M parameters and 3.00 GFLOPs per frame (was 6.97 M and 4.28).
- `encoder_backbone: simple` keeps the original small CNN, but trainable.
- New configs: `configs/remote_ir_fast_enc_{simple,resnet18}.yaml` (Anti-UAV300) and
  `configs/antiuav410_ir_enc_{simple,resnet18}.yaml` (Anti-UAV410). On your machine, set
  `encoder_pretrained_path` to wherever you put the weights file.
- Tests: `tests/test_encoder_training.py` (encoder gets gradients in stage 1, is frozen in stage 2,
  ImageNet weights load exactly; default config still keeps it frozen).

**For the paper.** This is a real design choice to report: "random frozen encoder" vs "trained
encoder" vs "ImageNet-initialised encoder" is now ablation row A11/A12.

**Second finding for the paper.** On both datasets 99.9% of detections come from motion crops; edge and
grid crops produce essentially none. The multi-source crop claim needs evidence from frames where those
crops matter (drone entering at the frame edge, re-appearing after occlusion), or it must be toned down.


## 9. Post-processing, tracker de-duplication, joint training, native resolution (13 Oct)

First honest Anti-UAV410 test result (ResNet-18 encoder, all four stages, tracker off): tracking
accuracy 47.2, mAP@50 72.4, mAP@75 30.1, precision 74.8, recall 73.7. Best tracker (SiamDT): 68.2 / 82.8.
Three problems found, three fixes:

- **Duplicate boxes, and the tracker made it worse.** One drone is often found by two or three
  overlapping crops. With the tracker on, false positives per frame went from 0.25 to 1.26 and
  precision from 74.8 to 46.0, because duplicates became extra tracks and extra guided crops.
  New: `drishti_v2/evaluation/postprocess.py` (NMS across crops, optional top-1 per frame).
  `run_sequence_eval.py` gets `--nms-iou`, `--top1`, `--save-raw`, and now feeds the tracker the
  de-duplicated boxes. `scripts/sweep_postprocess.py` picks NMS / top-1 / threshold on VAL and
  applies the choice once to TEST (the test set is never used for choosing).
  `scripts/run_all_stages.py` does all of this automatically after training, and `--eval-only`
  runs it on an already trained model.
- **Stages 2 to 4 add nothing.** Val mAP@50 is 78.3 after stage 1 and stays about 78 after the
  temporal, MoE and finetune stages. The old +31 "temporal jump" was compensating for the random
  encoder. New: `--schedule joint` trains every module together in one stage from the start
  (`--epochs joint=40`), to test whether the temporal and MoE modules help when they learn
  alongside the encoder. If they still do not, the paper must drop or reframe those claims.
- **Boxes are not tight enough** (mAP@75 30 vs SiamDT 46). We shrank 640x512 frames to 448x448,
  which makes tiny drones even smaller. New config `configs/dgx_antiuav410_enc_resnet18_640.yaml`
  trains at native 512x640.

Tests: `tests/test_postprocess_joint.py`. All tests pass except the old OpenCV visualization test.

## 10. Chain-of-Focus refinement, two versions (14 Oct)

**Why.** Round 2 on Anti-UAV410 test: best model (ResNet-18 encoder, joint training, 448) reaches
tracking accuracy 55.8 with the val-chosen threshold, about 9th of 18 next to the trackers; SiamDT 68.2.
Our biggest measured gap is box tightness (mAP@75 31 vs 46), and making the whole frame bigger
(512x640) did not help. Idea taken from Chain-of-Focus for VLMs (arXiv:2505.15436): look again,
closer, where the target is, and learn when another look is not needed.

**What it does** (`drishti_v2/models/focus.py`): for the top 2 boxes of each frame, cut a window of
3x the box size around the box, resample it to 64 px (a zoom-in), run it through the same crop
encoder, and predict a corrected box.
- `focus_mode: fixed` (version 1): exactly one closer look per candidate.
- `focus_mode: adaptive` (version 2): up to 3 looks; a small "stop" head predicts whether the current
  box is already tight (IoU >= 0.7 with the drone), and the candidate stops as soon as it says so.
- Training needs no reinforcement learning: input boxes are the true box shifted and resized at
  random (plus the model's own best box); the target is the true box; the stop target is
  "IoU(input box, true box) >= 0.7". The trainer adds the loss automatically.
- Cost: fixed version 3.33 GFLOPs per frame (3.00 without focus: two extra 64 px crops); the adaptive
  version uses 2 to 6 extra crops per frame depending on its stop decisions, and the evaluation now
  reports `focus_windows_per_frame`. Parameters: +0.07 M.
- Training memory: about 5 GB per run at batch 16, so both versions fit on one GPU together.
- Configs: `configs/dgx_antiuav410_focus_fixed.yaml` and `configs/dgx_antiuav410_focus_adaptive.yaml`.
  Compare against `a410_joint448_s42` (same everything, no focus).
- Tests: `tests/test_focus.py` (only the top 2 boxes change, gradients reach the focus head and the
  shared encoder, the trainer logs the focus loss, the module learns to re-centre a toy target).

**For the paper.** Cite and separate from: Dynamic Zoom-in Network (CVPR 2018), AdaZoom, recurrent
glimpse models (2014), Cascade R-CNN (iterative box refinement); in VLMs Chain-of-Focus, ZoomEye,
CropVLM. Our difference: causal streaming video, tiny targets, a fixed compute budget with a learned
stop decision.

## 11. Version 3: use the layers that know where the drone is (14 Oct)

**Why.** Studies of vision-language models find that shallow and middle layers are better than deep
ones at locating objects (counting, positioning, localization), while deep layers are better at
meaning (EMNLP 2025, "Multimodal Language Models See Better When They Look Shallower"; ICLR 2025
logit-lens study of LLaVA). Locating the drone tightly is exactly our weak point (mAP@75). In the
original design the box head reads only the very last module (MoE), which sits on the deepest encoder
layer pooled to 4x4. Our network is shallow (about 10 layers), so this is closer to the old detection
lesson behind FPN and hypercolumns than to "forgetting" in a 30-layer model: a cheap, sensible change
to be backed by an ablation, not a headline contribution.

**What changed** (both off by default):
- `head_layer_mix: true`: the head reads a learned weighted mix of three layers: encoder output,
  temporal output and MoE output (`LayerMix` in `detection_head.py`). The learned weights show which
  layers the model relies on (a small figure for the paper).
- `head_fine_features: true`: the box branch also gets the encoder's layer1 features (16x16 per crop,
  shallower and higher resolution), pooled to 4x4 and projected. Needs the ResNet-18 encoder.
- Config: `configs/dgx_antiuav410_layermix.yaml` (4.83 M parameters; compare with `a410_joint448_s42`).

**Diagnostic** (`scripts/probe_layers.py`, no training): on a trained model, fits a linear box
predictor from each of five layers (encoder layer1, layer2, encoder output, temporal, MoE) and reports
how well each one locates the drone inside the crop. If an earlier layer beats the MoE output, the
later modules are losing location information.

## 12. Version 4: close the gap to the top two (15 Oct)

**Results that led here** (Anti-UAV410 test, tracker off, raw output): Chain-of-Focus (fixed) beat the
reference on every box metric: mAP@50 76.2 vs 73.2, mAP@75 35.1 vs 31.4, tracking accuracy 49.9 vs
47.8. That is 3rd of 18 on mAP@50 and mAP@75 next to the trackers. The adaptive version was no more
accurate but used about twice the focus crops; the layer-mix version (11) gave nothing, and the layer
probe showed later layers locate the drone better (MoE 0.751 > temporal 0.716 > encoder 0.700 >
layer1 0.675), so version 3 is dropped. Compared with SiamDT and GlobalTrack, the gap is mostly:
- **coverage**: in 13.4% of test frames the drone is inside none of our crops (the motion heatmap peak
  is near the drone in only 61% of frames: hovering drones, a camera following the drone);
- **flicker and jitter**: our detection switches on/off in 10.6% of frames (trackers: 0%), and the box
  moves more between frames (temporal IoU 0.60 vs 0.72);
- **box tightness**: mAP@75 35 vs 46.

**What changed** (all optional; nothing changes unless switched on):
- **A. Memory crops** (`TargetMemory` in `drishti_v2/tracker/tracker.py`; evaluator `--memory`): after a
  confident detection, keep two crops (predicted position and last seen position) for up to 30 frames,
  even when the motion cue disappears.
- **B. More crops** (evaluator `--num-crops 12`): a larger crop budget at inference; no retraining.
- **C. Temporal smoothing** (`smooth_sequence` in `postprocess.py`; evaluator `--smooth`): one box per
  frame, smoothed when it overlaps the previous box, and held for up to 8 frames through a dropout.
  The validation sweep now also chooses whether to smooth, and reports the test result with and
  without smoothing.
- **D. Recurrent heatmap** (`heatmap_recurrent: true`): the motion network also receives its own previous
  heatmap as one extra input channel, so it can keep firing on a drone that stops moving. Needs
  training.
- **E. Second focus step** (`focus_max_steps: 2` with `focus_mode: fixed`): two closer looks per
  candidate; training now trains every step of the fixed version too. Needs training.
- Driver: `scripts/run_all_stages.py --seq-eval-args "..."` passes options to every sequence evaluation,
  and `--eval-tag NAME` writes results to `sequence_eval_NAME` so earlier results are kept. It also runs
  the tuned post-processing without the tracker (`summary_test_no_tracker_tuned.json`).
- Config: `configs/dgx_antiuav410_v4.yaml` = Chain-of-Focus fixed + D + E (4.64 M parameters).
- Tests: `tests/test_v4.py`.

**Which baselines are the right ones.** Our model never gets the first-frame box (the challenge's Track 2
setting). The 17 trackers we scored all get it (Track 1), so their table goes in the paper only as
"for reference". The main comparison must be detectors trained and tested the same way on Anti-UAV410:
DEIM/D-FINE, YOLO11, the 2025 challenge winner, YOLOV++, CHAL, MOCID, and Gaze-DETR (currently only
cited). These are tasks B1 to B6 in `STUDENT_TASKS.md` and are now the most important missing piece.

## 13. Track-1 mode: a like-for-like comparison with the trackers (15 Oct)

**Why.** The 17 Anti-UAV410 trackers are given the drone's box in the first frame (Track 1); our model
is not (Track 2). Comparing them directly favours the trackers. The fair way to compare is to give our
model the same first-frame box.

**What changed** (`run_sequence_eval.py --init-first-box`, evaluation only, no retraining): for the
first frame we output the given box (exactly what the trackers do: their frame-1 output equals the given
box), and we seed the target memory and the tracker with it, so our crops start on the drone. We use the
box only as a location prior; trackers also use it as an appearance template, so this is conservative
for us.

**In the paper:** two fair tables. Main table, Track 2 (no first-frame box): our model vs detectors
(YOLO11, DEIM/D-FINE, Gaze-DETR, the 2025 winner, ...). Second table, Track 1 (everyone gets the
first-frame box): our model in this mode vs the 17 trackers.

## 14. Results of 16 Oct, and version 5 (option A: a dense detector + our temporal parts)

**Results (Anti-UAV410 test, Track 2, post-processing chosen on val):**
- Best of ours: Chain-of-Focus fixed + memory crops + 12 crops: tracking accuracy 61.1, mAP@50 77.3,
  mAP@75 34.7, 4.0 GFLOPs per frame. Memory crops (+1.7) and 12 crops (+1.5) raised drone coverage from

- Version 4 failed (tracking accuracy 39.6, coverage 47 to 63%): the recurrent heatmap was trained on

- **YOLO11n (2.6 M params, 6.4 GFLOPs at 640): tracking accuracy 61.2, mAP@50 84.2, mAP@75 43.3.**

**Version 5, first form (evaluation only, no retraining):** YOLO11n decides "where", our parts work on

- YOLO's top boxes become guided crops for our model (the drone is inside a crop whenever YOLO saw it);
- optionally YOLO's boxes are also output (scores times W), optionally refined by our Chain-of-Focus head;
- our memory crops, tracker and the val-chosen post-processing stay on top.
Launcher: `dgx/run_v5.sh` (three variants: guided only, fused and refined, fused as is). If version 5
clearly beats YOLO11n, the next step is a trained version (our model trained with YOLO proposals).

**Also new:** `scripts/analyze_by_attribute.py` (detection rate and mean IoU per target size and per

## 15. 17 Oct: calibrated fusion (step 1) and version 6, a trained arbiter (step 2)

**Why.** Version 5 (YOLO's boxes + our temporal model) wins on tracking accuracy (65.2 vs 61.2 for
YOLO11n) but its box quality (mAP@50/75) stays slightly below YOLO alone. The reason is the
rule "highest score wins": our scores and YOLO's scores are on different scales, so sometimes our looser box
beats YOLO's tighter box. A hand-tuned rule is also not a research contribution. So we do two things:

1. **Calibrated fusion** (`scripts/sweep_fusion.py`, no GPU): re-uses the saved version-5 boxes and tries
   (a) scaling our scores down by alpha, and (b) "when both agree, keep YOLO's tighter box". Chosen on val,
   applied once to test. This is the cheap fix and becomes the strong *hand-made* baseline for step 2.
2. **Version 6, learned arbitration**: a small network decides per frame *which source to trust*:
   appearance (YOLO), motion (our model's crops), or memory. Three new pieces:
   - `drishti_v2/experiments/dump_candidates.py` runs the version-5 setup frame by frame and saves every
     candidate box (12 from our crops, top 3 from YOLO) with 25 simple cues: which source, its score,
     heatmap strength at the box, whether the other source agrees (overlap), whether it agrees with the
     previous frame, distance to where the memory expects the drone, box size, and so on. Plus the true box.
   - `scripts/train_arbiter.py` trains the arbiter on these cues: label = "this candidate overlaps the
     true box (IoU >= 0.5)". Two designs: `mlp` (each candidate judged alone) and `attn` (candidates of the
     same frame look at each other, one attention layer, so it can learn "motion and YOLO agree here").
     It also scores, on exactly the same candidates, the simple rules (highest score, ours only, YOLO only)
     and the **oracle** (best candidate in hindsight), which is the ceiling for any arbiter.
   - `scripts/baselines/yolo_antiuav.py --predict-splits train,val,test` (YOLO on the train split; needed
     to teach the arbiter).

**One caution, handled.** Our model and YOLO were both trained on the train split, so on train their
scores are over-confident. The arbiter is therefore trained twice: on train (`--fit-on train`) and on half of
val with the threshold chosen on the other half (`--fit-on val`). Test is never used for any choice.

**How to read the results.** The paper claim needs: arbiter > calibrated fusion > plain version 5 > YOLO,
on test tracking accuracy *and* mAP. The gap between the arbiter and the oracle says how much is left.
If the arbiter does not beat calibrated fusion, the learned part is not worth claiming.

Run: `dgx/run_v6.sh` (all of it, one command; about 1 day on one GPU). Tests: `tests/test_v6.py`.

## 16. 17 Oct: frame-dynamics YOLO11n baseline

**Why.** The 2025 Anti-UAV challenge winner showed that simply giving a detector frame differences as
input is very strong. A reviewer will ask "why not just do that?". So we test exactly that idea with the
same detector, data and training recipe as our YOLO11n baseline, so the only difference is the input.

**What changed.** `scripts/baselines/yolo_antiuav.py --frame-dynamics`: each input image becomes three
channels: the current frame, the amplified difference to the previous frame, and to 3 frames back
(`--dyn-gap`). Only past frames are used, like our model. Training images are written once to a separate
folder; at prediction the same images are built on the fly (the colour order is matched to what YOLO
sees in training). Everything after that (scoring, val-chosen post-processing) is unchanged.

**How to read it.** If this simple baseline matches the v6 judge, the judge is not worth claiming. If the
judge wins, it is the strongest evidence that *deciding which expert to trust* matters more than mixing
motion into one detector.

## 17. 17 Oct, evening: version 6 results, and version 7 (a learned "second look")

**Version 6 result (Anti-UAV410 test).** The learned judge gives nothing over the tuned rule (65.6 vs
65.7 tracking accuracy), and even a perfect choice among the same candidates reaches only 66.7. So
*choosing* between sources is not where the gain is. Two judges trained on the train split failed
(our model and YOLO are over-confident on their own training data), as predicted in section 15.

**Frame-dynamics YOLO11n** (section 16) is the strongest single model so far: 63.5 tracking accuracy,
87.8 mAP@50 at the cost of YOLO11n alone (+2.3 and +3.6 over plain YOLO11n). This is the 2025 challenge
winner's idea, so it is a baseline, not our contribution.

**What limits us now.** The oracle has 89.1 mAP@50 but only 66.7 tracking accuracy: the drone is found in
about 90% of frames, but the boxes are loose. Tracking accuracy is basically the mean overlap, so tighter
boxes are the lever. Chain-of-Focus tightened OUR boxes but hurt YOLO's, because it was never trained on
YOLO's boxes.

**Version 7** = frame-dynamics YOLO + a small refiner trained on YOLO's own boxes:
- `scripts/analyze_candidates.py`: first, the ceiling. For each frame, the best overlap any candidate has
  with the true box, binned into complete misses (< 0.1, need better proposals) and near misses (0.1 to
  0.5, a refiner can rescue), by target size. Minutes, no GPU.
- `scripts/train_box_refiner.py`: crops a window around each detector box from the frame-dynamics image
  (frame + 2 motion channels), and learns to shift and resize the box to the true box (smooth-L1 + GIoU).
  Trained on the train split (detector boxes with overlap >= 0.3, plus jittered true boxes), then applied
  to every val/test box; scores unchanged; the usual val-chosen post-processing gives the test number,
  directly comparable with the detector alone. Starts as "leave the box alone" (zero-initialised head).
- `dgx/run_v7.sh`: all of it, side by side with round 7 on the same GPU.

**How to read it.** Detector alone: 63.5 track / 87.8 mAP50 / 43.4 mAP75. The refiner is worth keeping if
mAP75 rises clearly (> 50) and tracking accuracy with it. If the ceiling analysis shows mostly complete
misses, refinement cannot help those frames and the next step is better proposals, not tighter boxes.

## 18. 17 Oct, late: motion-encoding ablation and the annotation-noise check (backlog ideas 2, 3, 4, 6, 8)

**Why.** Frame-dynamics YOLO showed that *what motion the detector sees at its input* is the biggest lever
we have found. Before building anything bigger, we measure that lever properly, with one change at a time.

**What changed.** `scripts/baselines/yolo_antiuav.py --motion-encoding {diff, flow, timesurface}`
(`--frame-dynamics` = `diff`), `--dyn-gap k`, `--box-gain`:
- `diff`: [frame, |diff t-1|, |diff t-k|]; the gap k is now swept (3 = the existing run, 5, 8). Slow or
  hovering drones vanish from a 1-frame difference but not from a k-frame one.
- `flow`: [frame, |diff t-1|, optical-flow magnitude], computed at half resolution (Farneback). This is the
  2025 challenge winner's input, so it makes our stand-in for that baseline as strong as the real one.
- `timesurface`: [frame, |diff t-1|, a decaying trace of recent motion] (max of the decayed previous trace and
  the current difference), borrowed from event-camera "time surfaces". The trace is carried frame to frame
  within a sequence, so training images are written in sequence order.
- `--box-gain 15`: YOLO's box-loss weight doubled (default 7.5), the cheap test of "care more about tight boxes".
- `winner`: [frame, signed diff to t-1, signed diff to t-2]. **This is the exact input of the 2025 challenge
  winner** (arXiv 2505.04917, Eq. 1; their ablation found differences beat optical flow in every case). Our
  frame-dynamics run (section 16) differs from it only in details (lag 3, absolute value, gain 4), so it is a
  near-reproduction of their idea, *not ours*. The paper's baseline row must say so.
All six runs use the same detector, data, epochs and val-chosen post-processing (`dgx/run_motion_inputs.sh`).

**Where that leaves the contribution (17 Oct, honest).** Nothing measured so far beats a winner-style input.
What is still open and would be ours: whether our motion network adds anything on top of it (round 7), the
learned refiner and the ceiling (round 8), and the track-before-detect idea for the frames no detector finds.

**Annotation-noise check** (`scripts/check_annotation_noise.py`, no GPU): how far are Anti-UAV410's own
boxes from (a) a smooth trajectory fitted through them and (b) the thermal blob they enclose? A predictor
cannot beat the labels' own consistency, so the mean IoU of (a) is an upper bound on tracking accuracy and
its share >= 0.75 an upper bound on mAP@75, per target size. If that bound is close to where we are, pushing
box tightness further is wasted effort and we say so in the paper.

## 24. 21 Oct: a scoring flaw found by the ablations, and the fix (affects every row)

**What the ablations showed** (laptop, same candidates, every row re-tuned on val, test once):

| | Track |
| --- | --- |
| our network only, per-frame / + decoder | 63.1 / 63.5 |
| gap-8 YOLO only, per-frame (threshold 0.02 allowed) / **+ decoder** | 66.7 / **69.4** |
| both, per-frame / + decoder | 68.5 / 68.7 |

The decoder on YOLO's boxes *alone* beats the two-eye system, and per drone size and attribute the YOLO eye
alone finds the drone at least as often as both together (except scale variation). Every val choice went to
the lowest threshold or "never absent".

**Why.** The Anti-UAV tracking accuracy subtracts 0.2 x (share of drone frames with no output)^0.3, which
punishes even a few empty frames hard. Our scorer only let methods choose thresholds of 0.1 and above, so
every detector lost points for frames where its best box had a lower score. Our network always outputs a box,
so part of its "+3" was simply filling those frames, not finding more drones.

**Fix.** `scripts/sweep_postprocess.py` now also tries thresholds 0.001 to 0.05 (for every method), and
`scripts/decode_candidates.py --frames-root --raw-val --raw-test` runs the decoder on any detector's output.
`dgx/run_rescore.sh` re-scores every baseline both ways (CPU, 1 to 2 h). All tables are rebuilt from that.

**Consequence for the paper (to confirm with the re-scored baselines and seeds).** The contribution that
survives is the *temporal* one: a motion-aware detector (gap-k input) plus sequence decoding over its full,
low-score candidate pool (64.5 -> 69.4 for gap-8 YOLO11n, single seed; +2.7 over the best per-frame rule on the
same boxes). Our original motion network does not add accuracy on top under fair scoring. The "inside our
network" ablation rows are therefore deprioritised.

## 27. 21 Oct: why the threshold matters so much (the evaluation finding, quantified)

- Only **2.0%** of Anti-UAV410 test frames (2,622 of 129,691) have no drone. The tracking-accuracy metric is
  therefore ~98% "mean overlap on drone frames", plus a penalty of 0.2 x (abstention rate on drone frames)^0.3
  that punishes even rare abstention hard. A method that never says "absent" loses almost nothing on the 2%
  and avoids the penalty entirely.
- **All 17 published trackers never abstain**: 0.0 to 0.1% empty frames (SwinTrack-Tiny 1.0%). They are
  scored in exactly the regime that val chose for our detectors (threshold 0.001 = always output the top box).
- Detectors evaluated with a usual confidence threshold (0.1 to 0.5) are the only methods that abstain, and lose
  about 5 points for it (section 26). Under the same never-abstain regime every small YOLO with the gap-k
  input (69.2 to 70.1) is above the best tracker (SiamDT 68.2, given the first-frame box).
- Consequence: on this benchmark the metric does not measure presence detection at all. A fair comparison
  needs either the same abstention rule for every method, or a metric that scores absent frames separately.

## 29. 22 Oct: the new-framework pieces (from the literature review in PLAN_CVPR2027.md), all run in parallel

**A fact that reframes the motion input.** In the test labels the drone's centre moves only 2.5 px per
frame (median); in 21% of frames under 1 px. The camera follows the drone, so plain frame differencing shows
the *background* moving, not the drone. That is why longer gaps helped (the drone's displacement accumulates)
and why background subtraction failed.

**Built (`scripts/baselines/yolo_antiuav.py`), one run each in `dgx/run_framework.sh` (round 16):**
- `--compensate`: ego-motion compensation. The global background shift between consecutive frames is
  measured by phase correlation at quarter resolution (textureless sky falls back to "no shift"), accumulated,
  and every past frame is warped onto the current one before differencing. The cheap, input-level form of the
  decoupled-motion and feature-alignment papers (arXiv 2606.15286; DFAR, PR 2026). ~5 ms per frame.
- `--motion-encoding tprofile`: a temporal-anomaly channel: how unusual the pixel is against its own
  compensated history of 16 frames (robust z-score with median / MAD). The input-level form of DeepPro
  (arXiv 2506.12766), which detects dim targets as anomalies in each pixel's temporal profile.
- `--motion-encoding lcm`: a local-contrast channel (|5x5 centre - surrounding ring|), the classic prior.
- `--nwd c`: label assignment and box loss use a scale-adaptive normalized Gaussian Wasserstein distance
  instead of IoU (NWD, Wang et al. 2022; SimD, arXiv 2407.02394): boxes as Gaussians, metric
  exp(-distance / (c x target size)). IoU is unstable for 10-px boxes; this is the published fix for tiny
  objects (+4 AP on very tiny ones). Training only; evaluation unchanged.
- `--model yolov8n-p2.yaml --pretrained yolov8n.pt`: a stride-4 (P2) detection head, so a 10-px drone covers
  several cells instead of one; COCO weights transferred where shapes match. Control row: plain yolov8n.
Runs: compensation; compensation + NWD; compensation + temporal anomaly; compensation + local contrast; NWD
alone; P2 head (+ its control). If the pieces add up, the proposed framework is: compensated temporal evidence
at the input, a tiny-object head (P2 + NWD), the decoder and box smoothing on top.

run was under-trained. From now on every run trains the full schedule (`--patience 0`, the new default), and
the combination queue (round 17) was restarted with it, including a full-length compensation + NWD at gap 8.
Earlier early-stopped runs (gap 3, winner, box15, NWD, yolov8n, P2, all-frames) carry the same caveat and
were, if anything, under-reported. Also closed: rectangular training (Ultralytics disables shuffling with it,
so batches are runs of near-identical frames and training collapses to 62.4).

## 32. 22 Oct, night: the "full-length" run was the same model, and what that means

The compensation + NWD run retrained for all 40 epochs produced test predictions **bitwise identical** to the
run that stopped at epoch 22. Training is deterministic (seed 42), so the first 22 epochs are the same in
both, and Ultralytics' `best.pt` is the checkpoint with the best *Ultralytics val fitness*, which peaked
before epoch 22 in both runs. So the real confound is not early stopping but **checkpoint selection**: a
40-epoch run can end up predicting with an epoch-12 model whenever the later, low-learning-rate epochs do
not beat an early fitness peak, and that fitness has nothing to do with our test metric.

Fix (`--pick-weights val`, now the default in the combination queue): best.pt and last.pt both predict the
val split, and the checkpoint with the higher val tracking accuracy is used for test; the choice is recorded
in `weights_choice.json` and `cost.json`. A re-run of a trained model no longer retrains (`--force-train` to
do so), so re-predicting with the new rule costs ~1.5 h per run, not a training.

Results of the NWD constant sweep (compensation + NWD at gap 8, early checkpoints, test): c = 0.5: 69.98,
c = 1.0: 69.65, c = 2.0: 70.06, vs compensation alone 69.88. The zoom second look scored 61.89 (much worse;
closed, possibly an implementation issue, not pursued for lack of time).
